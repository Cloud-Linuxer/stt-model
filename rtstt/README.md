# rtstt: 오픈 모델 실시간 STT 서버 (CPU 우선)

WebSocket으로 **실시간 전사 + 화자분리 + 실시간 번역**을 오픈 모델로 제공한다.
WebSocket 하나로 시작 설정(JSON)을 보내고 오디오(바이너리)를 흘리면 토큰 응답(JSON)이 돌아온다(`model` 값은 어떤 것이든 받는다).
기본 구성은 **GPU 없이 CPU만으로** 동작하고, 필요할 때만 GPU를 작게(약 5–6GB) 쓴다.
GPU를 쓰는 `gpu-max`는 발화 끝 → 확정 지연 중앙값 255ms를 낸다(아래 "GPU 최대 성능").

## 구성 (프로필)

| 프로필 | 1차 인식 (임시 토큰) | 2차 인식 (확정 토큰) | 화자분리 | 번역 | GPU |
|---|---|---|---|---|---|
| `cpu` | Nemotron-3.5 streaming 0.6B int8 (CPU) | 없음 (1차 결과를 확정) | CAM++ (CPU) | Hy-MT2-1.8B Q4 (CPU) | 0 |
| `cpu-hq` | 위와 같음 | Qwen3-ASR-1.7B Q8 (CPU) | CAM++ (CPU) | Hy-MT2-1.8B Q4 (CPU) | 0 |
| `gpu-min` | 위와 같음 (CPU) | Qwen3-ASR-1.7B Q8 (**GPU**) | CAM++ (CPU) | Hy-MT2-1.8B Q4 (**GPU**) | 약 6GB |
| `gpu-max` | 위와 같음 (CPU) | Whisper large-v3-turbo (**GPU**, 배치 + 점진 확정) | CAM++ (CPU) | Hy-MT2-1.8B Q4 (**GPU**) | 약 4.7GB |
| `gpu-multi` | 언어별 (Nemotron / Whisper / Omnilingual) | 언어별 (Whisper turbo·large-v3 / Omnilingual / Nemotron) | CAM++ (CPU) | Hy-MT2 + MADLAD-400 (**GPU**) | 약 11GB |

```bash
./start.sh cpu        # 또는 cpu-hq / gpu-min / gpu-max / gpu-multi.  ws://localhost:8765/transcribe-websocket
```

필요한 것: Docker(llama.cpp 서버 이미지), `.venvs/cpuasr`(sherpa-onnx 1.13.8을 `--system-site-packages` venv에 설치),
`models/asr/`(sherpa-onnx Nemotron), `models/mt/`(Hy-MT2·Qwen3-ASR GGUF), `models/*.onnx`(CAM++).
모델 받는 곳은 아래 "모델 출처" 참고.

## 동작 방식

```
오디오 ─┬─> Silero VAD ── 250ms 휴지: 구간 닫기(확정, <end> 없음) / 500ms 무음: <end>
        └─> Nemotron 스트리밍 (오디오를 한 번만 처리, 모든 세션을 배치 디코딩) ─> 임시 토큰
구간 닫힘 ─> [2차 인식 Qwen3-ASR] ─> 1차 단어 시각에 맞춰 정렬 ─> 확정 토큰 ─> 화자 라벨 ─> 번역 대기열
```

- **임시 토큰**은 Nemotron이 바로 내보낸다. 구간이 닫히면 2차 결과가 올 때까지 1차 결과를 임시 토큰으로 계속 보여준다.
- **2차 인식**은 무음이 250ms 이어지면 미리 시작하고, 구간이 닫힌 뒤 1.5초(`--final-budget-s`) 안에 끝나지 않으면
  1차 결과로 확정한다. 과부하가 걸려도 정확도만 내려가고 지연은 일정하다.
- **화자분리**: 구간 단위 CAM++ 임베딩 + 온라인 클러스터링. 1.5초 미만 구간은 새 화자를 만들지 못한다.
- **번역**: 문장 끝, 화자·언어 전환, `<end>` 단위로 Hy-MT2 공식 프롬프트를 써서 스트리밍 번역한다. 앞 3문장은 대화 이력으로 넣는다.
- 언어: Nemotron 자동 판별, 토큰 언어는 문자 체계(한글/라틴/가나/한자)로 표시한다.
- **점진 확정**(`gpu-max`): 3초 넘게 이어지는 발화는 1초마다 구간 전체를 Whisper로 다시 읽고, 연속 두 번 일치하고
  0.6초 이상 지난 단어를 바로 확정한다(LocalAgreement-2). 구간을 자르지 않아 문맥이 유지된다.
  GPU 대기열이 4건을 넘으면 건너뛴다.
- **확정 우선 스케줄링**(`gpu-max`): Whisper 요청은 확정 > 점진 확정 > 임시 갱신 순서로 처리한다.
  작업자 하나는 확정만 처리하고, 대기 중인 확정 요청은 최대 16개를 한 배치로 디코딩한다(단건 결과와 동일).
- **VAD**는 세션마다 Silero 상태를 유지하며 새 프레임만 계산한다. 구간 경계는 저장된 확률로 판정하고, 꼬리 부분은 60ms 단위로 세밀하게 본다.
- **엔드포인트**: 기본 500ms 무음. 임시 결과가 문장부호로 끝나면 0.7배만 기다린다.
  시작 요청의 `endpoint_latency_adjustment_level`(0–3 → 1.0/0.8/0.6/0.4배), `endpoint_sensitivity`(±30%),
  `max_endpoint_delay_ms`(상한), `max_non_final_tokens_duration_ms`(점진 확정이 없을 때 구간 강제 분할) 옵션을 받는다.
- GPU 서버용 이전 방식(Whisper가 0.5초마다 재디코딩)은 `--asr whisper`로 남아 있다.

### GPU에서 시도했다가 버린 것

- **Nemotron을 GPU로**: 배포된 int8 ONNX는 CUDA로 지정해도 연산자가 CPU로 돌아간다. 원본(NeMo) 실행이 필요하다.
- **한국어 특화 Whisper (BuzzASR/korean)**: 한국어 이득은 작고(7.30→7.08%) 한·영 혼합이 무너진다(58.9%).
- **여러 구간을 30초 창 하나로 패킹**: 3배 빠르지만 경계에서 문장이 섞여 CER이 3.5%→3.7–10.2%로 불안정하다.
- **확정 결과를 80ms 무음에 미리 디코딩**: 버려지는 디코딩이 대기열을 늘려 오히려 느리다. 250ms가 낫다.

## 컨텍스트 (`context`)

시작 요청의 `context`로 인식과 번역을 편향시킬 수 있다. 형식:
`general` `[{key, value}]`, `text` 문자열, `terms` `[문자열]`, `translation_terms` `[{source, target}]`, 전체 10,000자(≈8,000토큰) 초과 시 400.

| 적용 대상 | 적용 방식 |
|---|---|
| 확정 토큰 (Whisper turbo / large-v3) | `general` → 프롬프트(96토큰), `terms` → hotwords(64토큰, 끝에 문장부호 보존). `text`는 ASR에 쓰지 않음(실측에서 해로움). 배치 디코딩은 같은 컨텍스트끼리 묶는다 |
| 번역 (Hy-MT2, 채팅형 LLM) | `translation_terms` → 용어집 프롬프트, `general` → 채팅형 LLM의 배경 설명 |
| 임시 토큰 (Nemotron) | 적용 안 됨 (sherpa-onnx NeMo 구현이 탐욕 디코딩만 지원). 확정 시 교정된다 |
| Omnilingual 언어, MADLAD 번역 | 적용 안 됨 |

확장 기능: `{"type": "context", "context": {...}}` 제어 메시지로 **스트림 도중 컨텍스트를 바꿀 수 있다**
(이후 확정되는 구간부터 적용). 대화 진행에 따라 RAG 검색 결과의 용어를 실시간으로 넣는 용도다.

  Whisper 출력 문체가 바뀌어(군말·문장부호 추가) 자막 정답 기준으로는 조금 나빠질 수 있다. **용어(`terms`)만 넣는 쪽이 안전하다.**

### 효과, 새 유튜브 세트 (세트 2, 컨텍스트는 정답 자막을 보지 않고 영상 제목·채널·설명에서만 추출)

| 사례 | 용어만 (2회 평균) | 용어 + 제목 + 설명 |
|---|---|---|
| 당뇨 설명 (닥터딩요) | 11.7 → 12.5%, 용어 재현율 74 → 93%, 번역에 HbA1c 15회 반영 | 11.2 → 11.3% |
| 경제 강연 (세바시) | 6.5 → 5.9% | 6.9 → **10.6%** |
| 행동경제학 (매몰비용) | 7.3 → 7.3% | 7.3 → 7.2% |
| 앱 소개 (링고튜브) | 31.4 → 31.8% (자막 누락 많은 영상) | 31.6 → 30.9% |
| 영어 인터뷰 (Hands & Voices) | 7.9 → 8.5% | 7.9 → **13.3%** |
| 스티브 잡스 연설 | 7.8 → 8.3% | 7.9 → 7.8% |

결론: `terms`는 고유명사·전문용어 재현율을 올리고 전체 오류율은 ±1%p 안에서 움직인다. `text`(영상 설명)를 Whisper 프롬프트로
넣으면 두 사례에서 4–5%p 나빠졌다. 그래서 기본값은 `terms`→hotwords, `general`→짧은 프롬프트이고, **`text`는 Whisper 프롬프트에 넣지 않는다**(받기만 한다).

### 컨텍스트를 붙이며 찾아 고친 버그

- **용어 프롬프트가 문장부호를 지웠다**: 용어 목록을 프롬프트로 주면 Whisper가 그 문체를 흉내 내 문장부호를 거의 안 찍었고(문장 끝 토큰 20 → 5),
  문장 끝에서 번역 단위를 끊는 구조라 번역 호출이 20 → 6회로 줄며 긴 단위가 출력 한도(512토큰)에서 잘렸다(번역 글자 수 4,661 → 470).
  수정: 용어 프롬프트 끝에 문장부호를 붙이고, 문장부호가 없어도 300자가 넘으면 휴지에서 번역 단위를 끊고, 출력 한도를 1,024토큰으로 올렸다.
- **Hy-MT2 서버 슬롯 컨텍스트 부족**: `-c 8192 -np 8`은 슬롯당 1,024토큰이라 긴 문장 + 대화 이력이 400 오류를 냈다. `-c 32768`(슬롯당 4,096)로 변경.
- **빈 번역 재시도**: 번역 결과가 원문의 25% 미만이면 용어집·이력 없이 한 번 다시 번역하고, 그런 쌍은 이후 대화 이력에서 뺀다.
- **Whisper 반복 환각**: "시작을 시작을 시작을…"이 수십 번 반복된 구간이 한 클립의 CER을 12% → 22%로 올렸다(온도 재시도를 꺼서 잡히지 않았다).
  반복(연속 4회 이상 또는 zlib 압축비 2.4 초과)을 감지하면 repetition penalty로 재디코딩하고 남은 반복은 2회로 접는다.
  점진 확정은 반복 구간을 확정하지 않는다.

## 화자가 쉬지 않고 이어 말할 때 (빠른 화자 교대)

화자 라벨은 원래 "조각(휴지로 나눈 ASR 구간)" 단위였다. 조각 하나에 두 사람이 들어가면 한 명으로 묶이고,
점진 확정으로 생긴 0.5–1.5초 조각은 새 화자를 만들 수 없어 기존 화자에 강제로 붙었다(그리고 점진 확정 조각은 화자 학습에 쓰이지 않았다).
간격을 바꿔 가며 만든 세트(`bench/make_turns_set.py`: 합성 2인·3인, 실제 유튜브 화자 5명 50–150ms 간격)로 측정하고 고쳤다.

고친 것: ① 라벨 단위를 VAD 발화 구간(200ms 휴지면 분리, 1초 미만 조각은 앞 구간에 합침)으로 변경, ② 4.5초 넘는 구간은
앞뒤 2초 블록의 임베딩 유사도(<0.30)로 화자 전환점을 찾아 단어 경계에서 분할, ③ 짧은 구간은 유사도가 낮으면 직전 구간 라벨을 잇고
새 화자는 만들지 않음, ④ 점진 확정 조각도 화자 학습에 사용.

| 시나리오 | 화자 정확도 (전) | 화자 정확도 (후) |
|---|---|---|
| 한국어 2인, 간격 0ms | 87% | 90% |
| 한국어 2인, 간격 100ms | 84% | 88% |
| 한국어 2인, 간격 200ms | **66%** | **95%** |
| 한국어 2인, 간격 400ms | 94% | 97% |
| 한국어 2인, 0.3초 겹침 | 89% | 94% |
| 한·영 3인, 간격 100ms | **45% (2명만 찾음)** | **89% (3명)** |
| 실제 화자 5명, 간격 50–150ms | 91% | 88% → 정답 정정 후 **91%** |
| (회귀) 합성 4종 / 실제 혼합 세트1 / 세트2 | 98–100% / 99% / 92% | 98–100% / 98% / 89% → 정답 정정 후 **93%** |

간격이 100ms 이상이면 90% 안팎, 겹치는 발화는 겹친 구간이 한쪽 화자로 붙는다(동시 발화 분리는 안 됨).
실제 화자 5명 세트가 내려간 것은 과분할이 아니라 정답의 오류였다 — 인터뷰 음원의 진행자 목소리가 출연자와 같은 화자로 표기돼 있었다
("안정화 패스" 절의 "거짓 회귀" 참고). 진행자 구간을 뺀 정답으로는 구간 단위 라벨링이 두 세트 모두에서 이전 방식보다 높다(`--diar-mode piece`로 이전 방식 선택 가능).

## 의미 기반 엔드포인트 (턴 종료 감지) 조사와 측정

의미 기반 턴 종료 감지로 이를 줄일 수 있는지 오픈 모델을 조사하고(`bench/eot_eval.py`), 우리 데이터의 휴지 지점에서 측정했다.

### 서버에 넣어 본 결과 (`--eot`, 턴 86개: 합성 38 + 실제 화자 혼합 48)

200ms 휴지에서 감지기에 묻고, "끝"이면 250ms에 `<end>`, 아니면 800ms까지 기다리는 2단계 규칙. 한국어 가설은 Namo(텍스트), 그 외는 smart-turn(음성).

| 판정 방식 | `<end>` 지연 p50 / p95 | 합쳐진(놓친) 턴 | 턴 안에서 끊음 |
|---|---|---|---|
| 무음 500ms (현재 기본) | 0.52 / 0.64초 | 20% | 30 |
| smart-turn만 | 0.39 / 0.59초 | 23% | 40 |
| Namo + smart-turn | 0.41 / 0.82초 | 27% | 43 |

지연은 0.1초 줄지만 턴 안에서 끊는 횟수가 늘어 **기본값은 무음 규칙으로 두었다**(`--eot`로 켤 수 있음).
오프라인 측정과 다른 이유는 두 가지다. 실시간 가설은 음성보다 0.3–0.6초 늦어 200ms 휴지 시점의 텍스트에 마지막 단어가 없고,
"턴 안에서 끊음"의 대부분은 완결된 문장 뒤의 휴지라 어떤 감지기도 "끝"이라 보는 본질적 모호성이다.
더 줄이려면 (1) 한국어 대화 데이터로 smart-turn(학습 코드·데이터 공개)이나 turn-1-mini를 미세조정하거나,
(2) 추측 2차 인식(Whisper, 250ms 휴지에 시작)의 정확한 텍스트에 Namo를 걸어 보류 판정에만 쓰는 방식이 남아 있다.
LiveKit eot-bench 한국어 설정(377턴)으로 재면 위 공개 벤치마크와 같은 기준의 수치가 나온다.

## 안정화 패스 (2026-10-10): 기능 추가를 멈추고 버그를 찾아 고친 것

목표는 "이상한 입력에도 세션이 죽지 않고 프로토콜 형식의 오류 응답(`error_code`·`error_type`·`error_message`)을 돌려주고, 오래 돌려도 자원이 늘지 않고, 같은 입력에 같은 결과"다.
엣지 케이스 테스트(`bench/edge_tests.py`), 회귀 게이트(`bench/regress.py`), 부하 시험(`bench/soak.py`)을 만들고 거기서 나온 것을 고쳤다.

### 찾아 고친 버그

- **홀수 바이트 프레임에 세션이 죽음**: `pcm_s16le`인데 프레임 바이트 수가 홀수면 `np.frombuffer`가 ValueError를 내며 연결이 끊겼다.
  남는 바이트를 다음 프레임에 이어 붙인다(스테레오는 채널 수 × 샘플 크기 단위).
- **지원하지 않는 언어 코드**(`language_hints: ["xx"]`)에 Whisper가 예외를 내며 연결이 끊김 → 시작 요청에서 지원 언어 60개 목록으로 검사해 400 `invalid_request`.
- **설정 값 타입 오류가 조용한 종료(1011)로 끝남**: 설정이 JSON 배열, `translation: "one_way"`, `context: "문자열"`, `num_channels: "two"`,
  엔드포인트 옵션이 문자열인 경우 등. 모두 400 `invalid_request`로 돌려준다. JSON이 아니거나 객체가 아닌 텍스트 프레임도 400.
- **컨텍스트 길이 검사가 JSON 문법까지 셌다** → 내용 글자 수만 센다(한도 바로 아래의 9,990자 `text`가 거절되던 문제).
- **장시간 스트림 메모리**: 세션이 오디오 전체를 들고 있어 300분이면 세션당 1.1GB → 절대 인덱스로 주소를 매기는 `AudioBuffer`로 바꿔
  아무것도 참조하지 않는 구간(가장 오래된 참조점 − 10초 이전)을 10초마다 버린다. 6분 스트림(번역·화자분리 포함) RSS 6.99 → 7.10GB로 평탄.
- **세션 상태 중 끝없이 자라던 것들**(코드 감사로 찾음): VAD 프레임 점수 목록(스트림 시작부터 32ms마다 1개 → 오디오와 같은 기준으로 잘라냄, `_soft_cut`도 오프셋 반영),
  번역 이력(최근 3쌍만 쓰면서 전부 보관 → 20쌍만 유지), 턴 텍스트(`<end>`가 없는 세션에서 무한 증가 → 300토큰 유지),
  Nemotron 림보 토큰(닫힌 구간보다 앞선 토큰은 영원히 남음 → 구간 닫을 때 함께 제거).
- **번역 서버가 죽으면 세션 종료가 밀림**: 호출마다 연결 타임아웃을 기다렸다 → 연결 타임아웃 2초, 연속 3회 실패 시 30초간 번역을 건너뛴다(전사는 계속).
  Hy-MT2 컨테이너를 내린 상태에서 오디오 끝 0.0초 후 `finished`, 로그에 "translation disabled" 2회.
- **실시간보다 빠른 입력(burst)이 다른 세션을 늦춤**: Nemotron 디코더가 한 호출에서 밀린 청크를 전부 처리했다 → 호출당 6청크(약 3초)로 제한하고 나머지는 다음 호출에서 처리.
- **벤치 클라이언트 버그**: 보내는 동안 받지 않아 ping 타임아웃으로 끊긴 것을 서버 오류로 잘못 봤다. 테스트 클라이언트는 전송 중에도 수신한다.

### 부하 시험 (`bench/soak.py`, 16스트림 × 10분, 화자분리 + 엔드포인트, 절반은 번역 포함)

같은 서버에서 두 번 연속 실행한다. 첫 실행은 세션 상태 할당과 할당자 워밍업을 포함하므로, **두 번째 실행의 증가분이 누수 판정**이다.

| | 1회 (콜드) | 2회 (웜) |
|---|---|---|
| 완료 스트림 / 오류 / Traceback | 16/16 / 0 / 0 | 16/16 / 0 / 0 |
| 서버 RSS 시작 → 끝 | 7.05 → 8.07 GB (+1.02, 그중 90초 이후 +0.20) | 8.07 → 8.24 GB (+0.17, 90초 이후 +0.04) |

단일 스트림(tok_final p50 1.57초)보다 0.5초 길다 — 원인은 아래 "성능 개선 패스"에서 프로파일로 찾았다.

### 아직 남은 것

- `<end>`는 여전히 무음 기준이다(의미 기반 감지기는 `--eot`로 선택).
- 16스트림 동시 처리에서 확정 토큰 지연 중앙값이 2.1초로 늘어난다(단일 1.57초) → "성능 개선 패스"에서 다룸.

### 거짓 회귀: "5명을 6명으로 나누는 과분할"

구간 단위 라벨링을 넣은 뒤 실제 5인 혼합 클립(세트 2)의 화자 정확도가 0.915 → 0.885로 내려가 과분할로 기록했었다.
오프라인으로 정답 턴마다 CAM++ 임베딩을 뽑아 보니 네 화자는 같은 화자 안에서 유사도 ≥0.70, 다른 화자와는 ≤0.29로 깨끗했지만
화자 D(영어 인터뷰)만 같은 화자 안의 최소 유사도가 0.00이었다. 인터뷰 자막은 진행자와 출연자를 `- `로 구분하는데, 혼합 클립 생성기가
둘을 모두 "D"로 넣었던 것이다 — **6번째 화자는 실제로 있었고 정답이 틀렸다.** 자막의 `- ` 표시로 진행자 구간(18–31.6, 65.7–68, 78.4–82.7, 123.1–131.8초)을
제외하도록 생성기(`bench/clips_yt2.json`의 `mix` skip 범위, `make_turns_set.py`)를 고치고 다시 만들었다: 오프라인 모사에서 임계값 0.35–0.50 모두 정확히 5명,
서버 측정 화자 정확도 **0.933**(이전 방식 0.915보다 높다). 빠른 교대 세트의 실제 5인 파일도 같은 정정 뒤 0.910.

### 고친 것

- **적응형 재인식 간격**: 큐에 쌓인 GPU 요청 8건마다 기본 간격이 한 배씩 늘어난다(`--prog-load-queue`). 이전엔 큐 4건 초과 시 재인식을 **건너뛰어** 단어가 구간 닫힘(최대 6초)까지 기다렸다.
- **재인식 창 축소**: 열린 구간 전체(최대 30초) 대신 마지막 확정 단어 3초 전부터(`--prog-window-s`). 인코더 비용은 같지만 디코더 토큰 수가 준다. 60초 쉼 없는 발화 280/281자, 합성 CER 동일.
- **최종 디코드의 언어 감지 생략**: 다중 언어 힌트 세션은 디코드마다 언어 감지(인코더 1회 추가)를 한다. 한 구간의 재인식들이 모두 같은 언어를 냈으면
  최종 디코드는 그 언어를 재사용(구간당 인코더 1회 절약). 재인식 자체는 창마다 감지한다 — 처음엔 재인식도 재사용하게 했다가 구간 안에서 언어가
  바뀌는 빠른 교대(한·영 3인) CER이 나빠져 되돌렸다.
- **시도했다가 되돌린 것 — 점진 확정 조각을 열린 구간 전체 문맥으로 라벨링**: 간격 0.7초에서 0.7초짜리 조각을 그 오디오만으로 라벨링하면
  "짧은 단위는 새 화자를 만들지 않는다" 규칙 때문에 쉬지 않고 교대하는 두 화자가 한 명으로 붙었다(gap 0ms 0.539). 조각이 속한 열린 구간 전체를 문맥으로
  라벨링해 봤더니 더 나빠졌다(gap 200ms 0.943 → 0.726, 합성 잡음 0.996 → 0.952): 아직 자라는 마지막 단위가 매 확정마다 다른 길이로 중심점을 갱신해
  중심점이 오염된다. 조각 단위 라벨링으로 되돌리고 간격은 1.0초를 유지한다(그 조합은 0.89–0.95).
- **Nemotron 작업자 구성**: 6작업자×2스레드 → **8작업자×1스레드**. 16스트림 CPU 14.0 → **11.5코어**, 지연 동일 (2×6은 19.6코어로 악화 — onnxruntime intra-op 스레딩이 이 int8 모델에 비효율, 12×1은 이득 없이 RSS +2.5GB).
- **화자 임베딩 캐시**: 같은 구간을 0.5초마다 다시 라벨링할 때 이미 임베딩한 단위는 재사용, 아직 자라는 단위는 1초 이상 자랐을 때만 다시 임베딩. 최종 라벨은 항상 정확히 계산(오프라인 비교에서 라벨 동일).
- **운영 기능**: `/metrics`·`/health`(Prometheus 텍스트, 세션·오류·오디오 초·Whisper 디코드/점유/큐), 동시 스트림 상한(429 `limit_exceeded`), 300분 상한(413 `max_duration_reached`, 확정 결과 먼저), 유휴 타임아웃(408 `request_timeout`), SIGTERM 드레인, 시작 요청 검증(힌트 중복, 엔드포인트 옵션 범위, `client_reference_id` 256자, 바이너리 시작 요청). 엣지 테스트 33개 + 한도 테스트 4개(`--limits`).

## 남은 과제 조사 (2026-10-10): 해결 가능한 것과 아닌 것

2026년 10월 기준 공개 모델·데이터·라이선스를 조사하고, 후보마다 사실 확인과 우리 파이프라인 적합성 반박 검증을 거쳤다. 검증을 통과한 결론만 적는다.

| 과제 | 판정 | 경로 | 근거 |
|---|---|---|---|
| 수용량 (16 → 32–40스트림) | 가능 | Whisper 인코더 창 축소 + Nemotron 1차 인식을 GPU로(NVIDIA NeMo-Speech.cpp, Apache-2.0, CUDA Q8 배치). 둘을 함께 해야 한다 | 재인식 창은 15–20초 바닥이 필수(3초 마진은 발화 중간 창 23개 중 11개가 반복 루프) → 디코드 59 → 38–42ms. int8_float16은 RTX 50xx + CTranslate2 4.6에서 단어 정렬이 실패해 제외. 두 번째 GPU는 이 보드에 CPU 직결 슬롯이 하나뿐 |
| 번역 품질 | 가능 | 측정을 XCOMET-XXL/CometKiwi + GEMBA-MQM으로 바꾼 뒤(현 chrF는 모든 모델이 56–57로 포화) Hy-MT2-7B Q4_K_M(Apache-2.0, 실측 237 tok/s, VRAM 7.1GB) → Gemma 4 12B QAT Q4 시험(실측 152 tok/s, VRAM 11.7GB) | en→ko XCOMET-XXL 88.5 → 92.0. Gemma 4 12B는 한국어 문맥 번역 커뮤니티 벤치에서 MQM 페널티 0.86 vs Hy-MT2-7B 1.86 |
| CPU 한국어 정확도 | 부분 | Nemotron-3.5 미세조정(.nemo 공개, OpenMDW-1.1, 공식 노트북, sherpa-onnx 재export → 런타임 동일), 영어 리플레이 필수 | 보고된 이득 31–34% 상대 → CER 6–9% → 4.5–7%. Whisper 수준은 CPU에서 불가. 한국어 ITN(숫자 변환)은 Nemotron 출력에 띄어쓰기가 없어 실측 이득 0(이론 상한 1.1%p) |
| 의미 기반 `<end>` | 부분(작음) | Scicom(≈13%, 이미 포함)을 eot-bench 한국어로 측정하고 "미완결이면 연장" 정책만 | 1차 가설 지연 p50 0.36 / p90 0.44초라 300ms 단축은 불가(마지막 단어가 없으면 Namo 완결 확률 0.00) |
| 겹침 발화 | 사실상 불가 | 현 동작(겹친 구간을 한 화자에 붙임)이 업계 표준. pyannote segmentation-3.0은 합성에서는 되지만 실제 4인 세트에서 경계 29개 중 15개만 검출 | 적용하면 실제 세트(0.87)가 회귀할 가능성이 크다 |
| 확정 지연 1.55초 | 지금은 불가 | Voxtral Mini 4B Realtime(Apache-2.0, 한국어 포함, 480ms 지연 설정)은 p50 약 0.8–0.9초가 가능하지만 FLEURS-ko WER 15.7 vs Whisper 14.3, 한·영 전환 붕괴, vLLM 다중 세션 버그(세션 길이 상한·데드락·수 분 공백) 미해결 | 6개월 뒤 재평가. AlignAtt 하드 커밋은 저자 데이터상 1.3–1.5초로 이득 10% 이하 |

조사 중 돌린 한국어 전용 스트리밍 Zipformer(`kangkyu/icefall-asr-ko-streaming-zipformer-174m`, Apache-2.0)는 `bench/asr_models/sherpa_kozip*.py`로 추가했다:
실제 한국어 CER 11.9%로 Nemotron(11.9–12.4%)과 같고 CPU는 4.8배 싸지만(RTF 0.048 vs 0.230) 영어 WER 99.9%라 한국어 전용 용량 옵션일 뿐이다.

## 한계

- CPU 1차 인식(Nemotron)은 실제 한국어 대화에서 Whisper GPU보다 CER이 2–5%p 높다. CPU만으로 정확도를 올리려면 `cpu-hq`(1–2스트림)를 쓰거나,
  한국어 대화 데이터로 Nemotron을 미세조정해야 한다.
- 첫 토큰 지연은 1차 모델의 처리 단위에 묶여 있다: 560ms 모델 0.88–1.00초, 320ms 모델(GPU 프로필 기본) 0.68–0.90초. 수백 ms로 더 줄이려면 160ms 모델과 CPU가 더 필요하다.
- 동시 발화(겹침)는 처리하지 못한다. 구간 하나에 화자 한 명만 붙는다.
- `<end>`는 VAD 무음 길이로 판단한다(의미 기반 감지 `--eot`는 실험 옵션).
- 오디오 포맷은 `pcm_s16le`·`pcm_f32le`만 받는다.
